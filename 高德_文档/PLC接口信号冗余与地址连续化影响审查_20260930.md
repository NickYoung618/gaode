# PLC接口信号冗余与地址连续化影响审查

日期：2026-09-30

本文整理本会话的问题讨论，不代表批准修改协议或实施代码变更。本次仅新增本记录，不修改来源协议、项目源码、功能规格或任务勾选。

## 1. 结论与审查范围

目前可以确认：项目存在信号定义和解释规则的重复维护；地址改为连续后，不能只修改一张地址表。

需要区分两件事：

- **实现中的重复定义**：同一信号的地址、编码或解释规则在多处维护。
- **协议中的多余信号**：某个信号是否能够删除，并且不损失必要的业务或握手信息。

前者已有明确证据；后者只能列出需要核对的重叠候选，不能仅凭名称相近就删除。

审查依据是本会话前期已读取的现行协议、源码及009规格中的审查记录。回答问题时，补充全仓扫描受到环境执行策略限制，因此文件数量只给出已确认下限，不作为完整迁移清单。此次权限恢复后仅保存讨论记录，未补做全仓扫描或运行验证。

## 2. 已确认的定义冗余

| 问题 | 具体位置与表现 | 影响 |
| --- | --- | --- |
| 两端分别维护信号表 | Host的`ProtocolLatestMap.cs`与VirtualPlc的`PlcAddressMap.cs`分别维护同一套协议定义 | 修改信号时需要人工保证两份一致 |
| 地址表之外又存在隐含映射 | `LatestProtocolPlcDevice.cs`同时使用命名常量、固定读取范围和裸数组下标 | 修改常量后，部分实际读写仍可能使用旧地址 |
| 协议状态含义由多处解释 | 通信实现解释原始状态；`MotionCoordinator.cs`等业务代码又判断夹紧值`1`、检测值`0`等 | 状态编码变化会影响业务层，可能出现解释不一致 |
| 数据编码规则重复实现 | Host有`ProtocolLatestFloat32`，VirtualPlc的`PlcDataStore`另有浮点编码实现；009审查记录也指出此项 | 字序、编码调整需要同步两端 |

现有PLC轮询代码包含以下访问方式，末行仅节选表达式：

```csharp
var coils = await wire.ReadCoilsAsync(0, 16, ct);
var r = await wire.ReadRegistersAsync(0, 0x53, ct);
// 安全条件中的部分表达式：
// coils[4] && !coils[3] && !coils[15]
```

其中`coils[15]`绑定了当前人工区域占用信号的位置。这个下标本身就是一份没有命名的地址定义。即使修改`ManualZoneOccupied`常量，这一处也不会自动变化。

因此，“由上位机统一制定协议”已经明确，但“软件只有一处维护协议定义”目前没有做到。

## 3. 协议信号本身是否多余

| 信号组合 | 当前判断 |
| --- | --- |
| `XY_Pos_Confirmed`与`Z_Axis_Move_Status=2` | 存在到位信息重叠，值得核对；如果分别表达XY与当前Z轴的到位条件，就不能直接合并 |
| `PLC_System_Fault`、`Alarm_Bits`、`Alarm_Severity` | 都参与故障判断，但可能分别承担总故障、故障明细和等级。需要明确相互关系，才能判断是否存在可推导的重复状态 |
| `Retry_Cmd` | 属于需要核查的遗留候选：当前故障恢复采用“双端复位后完整新轮”，旧协议中的当前动作重试语义需要核对。仅凭地址表中存在它，不能断言仍在使用或可以删除 |
| `Flip_Status`与`Flip_OK` | 当前协议下职责不同：前者报告动作状态，后者表示上位机已核验并要求清零 |
| `Sorting_Exec_Status`与`Sorting_OK` | 分别承担完成反馈与确认清零两个职责 |
| 命令与反馈，例如`Pallet_Lock_Cmd/Status` | 分别表达“要求设备做什么”和“设备实际处于什么状态”，不能作为重复信号删除 |

当前能够明确认定的是实现层面的重复维护。业务信号层面已有重叠候选，但现有审查不足以给出“可以删除多少个信号”的结论。

信号删减还需要核对PLC实际实现、状态产生条件、写入责任、清零责任和现有消费者，不能编造缺失的握手或业务规则。

## 4. 改为连续地址至少涉及多少文件

### 4.1 计数前提

本节仅讨论：**保持信号含义、数据类型及Coil/Register分区不变，将各区内地址空隙压缩，按原顺序连续排列。**

在这一前提下，本会话已读取的证据能够确认，至少涉及以下3个核心源码文件：

| 文件 | 调整原因 |
| --- | --- |
| `backend/src/Gaode.Infrastructure/Devices/Plc/ProtocolLatestMap.cs` | Host信号地址需要更新 |
| `VirtualPlc/PlcAddressMap.cs` | 模拟下位机需要采用相同的新地址 |
| `backend/src/Gaode.Infrastructure/Devices/Plc/LatestProtocolPlcDevice.cs` | 固定下标、读取范围、部分读写偏移需要同步；例如人工占用信号压缩地址后，`coils[15]`就会读取错误位置 |

**3个只是已确认的下限，不表示修改这3个文件即可完成迁移。** 该数字不包含尚未逐项核实的测试、脚本、文档及其他消费者，也不包含真实PLC工程。

### 4.2 还需逐项检查的影响范围

- `StagePortContracts.cs`：009已记录其中包含协议地址和完成值。
- `LatestProtocolStageActionAdapter.cs`：分拣、下料、解锁等实际读写及诊断是否依赖旧布局。
- VirtualPlc执行、存储和监控代码：是否全部通过地址表访问，是否仍有独立地址或布局假设。
- 协议测试和联调脚本：独立预期地址、报文核对及监控解析需要与新基线核对。
- 现行协议及直接相关的spec、contracts、plan、tasks：应明确新旧协议基线及消费者影响；历史证据应保留原版本，不能批量改写成新协议证据。

以上属于待核实影响范围，不能在未完成扫描时全部计为“必改文件”。引用地址常量的文件也不一定需要修改，必须检查实际访问方式。

### 4.3 如果同时采用MW1000/MW3000及BOOL按位分组

如果“连续地址”还包括MW1000/MW3000分区、BOOL从Coil改为寄存器内的位，那么变化同时涉及存储区域、功能码或读写方式、位提取及可能的共字写入协调。

这已超出纯地址重排，不能直接沿用上述3个文件的计数范围。现有讨论稿也不能自动视为已批准的运行协议。

## 5. 为什么会影响多个文件

从已读代码能确认以下原因：

1. **协议表没有成为唯一映射入口。** 常量之外仍存在固定偏移、固定读取范围和数组下标。
2. **通信表示与业务判断没有完全分开。** 业务层仍理解部分原始协议数值。
3. **Host与VirtualPlc独立维护同一规则。** 当前主要依赖人工同步。
4. **已有传输封装没有解决语义隔离。** `PlcAdapter`只是转发寄存器读写，不能自动屏蔽地址和布局变化。

地址不连续本身并不必然导致这些问题。即使全部改成连续地址，只要上述重复维护方式仍然存在，下一次调整仍会影响多个文件。

按当前项目规模，可以讨论统一维护信号定义、将原始地址和状态解释集中在通信层，让业务消费稳定的设备含义。具体可以采用共享定义或生成方式，由实际成本决定；无需因此预建通用协议引擎。两端共享定义后，仍须保留依据协议原件的独立核对，避免两端共同使用同一份错误定义。
