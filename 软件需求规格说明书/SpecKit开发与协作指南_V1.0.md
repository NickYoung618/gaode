# Spec Kit 开发与协作指南（3～4 人）

日期：2026-09-20。本文是基于 V1.1 的开发组织建议，不修改已确认的业务范围。技术栈、成员姓名、远程仓库地址和真实设备参数仍待补充。

## 1. 当前状态与推荐方式

当前目录已有需求资料和 V1.1 说明书，尚未初始化 Git 仓库；本机已安装 Git、uv 和 Specify CLI，实查 CLI 版本为 `1.0.5.dev0`。本文提供操作示例，本次未执行初始化、安装、提交或推送。

推荐：一个仓库、一套公共接口、一名集成负责人；成员按模块负责，实际编码按短期功能分支推进。先合入公共基础，再并行开发，每完成一个可验证的小功能就提交合并请求（PR）。

Spec Kit 用来生成和维护需求、设计、任务及实现检查；分工、代码评审和合并由团队通过 Git 和仓库平台管理。不要把整个系统一次性作为一个实现任务，也不要长期保留互相脱节的“张三分支”“李四分支”。

团队开始前统一 Specify CLI、模板和项目运行环境版本。本机是开发版本，正式采用哪个版本由团队选定并记录；升级工具单独提交，避免成员自行升级导致生成文件不一致。版本固定方式见[官方安装说明](https://github.github.com/spec-kit/installation.html)。

## 3. 所有人共同遵守的范围

将下面约束写进 `.specify/memory/constitution.md`，每个功能 spec 引用相关条款：

1. 当前依据为 `软件需求规格说明书_V1.1_开发范围版.md`，开发任务保留原需求 ID。
2. X/Y 使用可替换的固定点位配置；3D 仅识别 Z 高度；光学对焦固定。
3. 算法调用具有有限等待和明确终态。失败、超时、未配置或无结果转为异常／Pending，继续下一可执行步骤；迟到结果不得重复触发物理动作。
4. 质量结果与流程完成状态分别保存。算法异常不是等待人工确认才能继续的理由。
5. MES、模型、样本仅预留空接口，返回明确的“未接入”；不实现相关业务页面、上传、训练或模型管理。
6. 交付、培训、验收及责任输入暂不参与开发。内部代码测试和合并检查用于开发质量，不新增对外交付或验收要求。
7. OPEN-01、OPEN-02、OPEN-04 按已确认决策执行；OPEN-03 和其他缺失细节保持“待补充”。
8. 待补充事项登记影响范围和可独立推进的任务。现场数值不明确时使用明确标识的模拟配置开发；不把模拟坐标写成真实设备参数。
9. 算法异常出口与设备安全控制分别处理。Z 无有效结果时，不使用猜测高度下发动作；按 OPEN-26 保留待补充分支，继续开发其他已明确功能。
10. 公共接口、状态枚举、数据库结构和依赖版本的变化必须由维护人评审，并同步相关 spec、plan 和调用方。

## 4. 先统一接口，再并行开发

A 组织 B/C/D 一起确定最小接口，提交到主分支。先确定数据含义、单位和异常状态，再确定最终方法名；下表只是建议命名。

| 接口／数据 | 必须约定的内容 |
| --- | --- |
| 任务身份 | TaskId、PartId、GroupId、FaceId、SlotId、AttemptId；外部工件码可空 |
| 固定点位 | PointId、配置版本、X/Y、Z 来源、单位、适用轴；模拟与真实配置分开 |
| 设备动作 | CommandId、动作类型、目标点、请求／完成／失败／取消；以 PLC 实际协议能力映射，不假设 PLC 已支持新字段 |
| 图像采集 | CaptureId、任务／工件／面、相机、图像引用、时间与采集状态 |
| 算法调用 | InvocationId、输入关联、有限超时、Success/Error/Timeout/NotConfigured 等执行状态；质量结论另存 |
| 业务结果 | OK/NG/Pending、原因、来源图像；融合细节缺失时登记待补充 |
| 流程状态 | 当前工步、已执行动作、可继续／待硬件处理状态；与质量结论分离 |
| 预留接口 | MES、模型、样本默认 NotIntegrated；不作为主流程就绪依赖 |

建议依赖方向：HMI 调用应用／流程入口；流程通过公共接口调用设备、算法和存储；真实适配器与模拟适配器实现同一接口。模块之间不直接读取对方的内部对象或内部数据库表。

B 可以先对设备模拟器开发，C 可以使用模拟设备和算法结果，D 可以使用模拟流程事件和存储数据。接口变化先提交一个小 PR，相关人员更新后再推进依赖它的实现。

## 6. 初始化示例

以下是供团队执行的 PowerShell 示例。先统一工具版本。以当前目录和 Codex 集成为例：

```powershell
Set-Location 'E:\dzk\gaode-1'
git init -b main
git add -- '高德_文档' '软件需求规格说明书'
git commit -m 'docs: record V1.1 requirement baseline'
git switch -c chore/speckit-bootstrap
specify init --here --integration codex --script ps
git status --short
git diff
```

当前目录非空，初始化可能询问是否合并生成文件；先保留上面的 Git 基线，再检查生成内容。`--force` 会允许覆盖冲突的受管路径，不应不经检查地反复初始化。操作依据见[现有项目接入指南](https://github.github.com/spec-kit/guides/existing-projects.html)。

A 随后建立 `.gitignore`，排除运行日志、采集图像、设备密码、本地数据库、构建产物及个人配置；检查 `git status` 中的新文件，提交规范和项目骨架。将仓库连接到团队使用的 Git 平台，完成首次评审和基线合入。其他人从统一仓库克隆，使用仓库中已有模板，不重复生成项目规范。

## 7. 每个功能如何使用 Spec Kit

下面的 `$speckit-*` 输入到 Codex 的对话框，**不是 PowerShell 命令**。其他工具的调用写法以对应集成为准，例如 Copilot 默认使用 `/speckit-*`；参见[官方集成说明](https://github.github.com/spec-kit/reference/integrations.html)。

项目规范由 A 先执行一次，全员审阅：

```text
$speckit-constitution
以软件需求规格说明书/软件需求规格说明书_V1.1_开发范围版.md 为当前需求基线。
把本指南第 3 节的已确认范围约束写入项目规范。
采用一个仓库、公共接口、功能分支和评审合并。
待补充项不得自行变成已确认值；已排除功能不加入开发任务。
```

每个功能依次执行，并在每一步检查输出。核心流程及各步骤作用见[官方工作流说明](https://github.github.com/spec-kit/reference/agentic-sdd.html)。

| 步骤 | 作用 | 谁负责检查 |
| --- | --- | --- |
| `$speckit-specify` | 生成本次功能的 `spec.md`，明确范围、业务行为及关联需求 ID | 功能负责人；跨模块内容由相关人审阅 |
| `$speckit-clarify` | 澄清本次需求；无法回答的细节保留待补充，拆出不依赖它的工作 | 功能负责人，业务决策由有权决定的人补充 |
| `$speckit-plan` | 使用团队统一技术栈形成设计、数据与接口方案 | A 与相关模块维护人 |
| `$speckit-tasks` | 生成任务，补充负责人、文件范围、依赖和完成检查 | 功能负责人 |
| `$speckit-analyze` | 检查 spec、plan、tasks 的一致性；按报告修正来源文件 | 功能负责人 |
| `$speckit-implement` | 分阶段实现指定任务，检查实际修改和运行结果 | 开发者 |
| `$speckit-converge` | 对照需求、计划和任务查漏；出现补充任务则继续实现后复查 | 开发者；之后仍须提交人工评审 |

如使用 `$speckit-checklist`，把它作为需求质量检查，由指定评审者核对。不要把模板生成的条目自动当成已经通过，也不要把缺失参数“检查通过”来绕过待补充事项。

### C 开发普通件流程的示例输入

```text
$speckit-specify
```

```text
$speckit-plan

```

```text
$speckit-tasks
每项任务写明负责人、关联需求 ID、允许修改的文件、前置任务和完成检查。
```

`[P]` 用于标识可并行的任务，人员和目录权限仍由团队明确分配。每人每次把当前功能和任务范围写清楚。

### 每次操作前确认 feature 目录

当前官方说明中，活动功能由 `.specify/feature.json` 或 `SPECIFY_FEATURE_DIRECTORY` 决定；切换 Git 分支不会自动切换功能。见[官方 Quickstart](https://github.github.com/spec-kit/quickstart.html)。

当 `specs/003-inspection-flow` 已生成且准备继续该功能时，可在启动工具的 PowerShell 中显式设置：

```powershell
$env:SPECIFY_FEATURE_DIRECTORY = (Resolve-Path '.\specs\003-inspection-flow').Path
```

随后从同一终端启动开发会话，使其继承环境变量。已打开的桌面应用不会自动继承这个终端的新变量；这种情况下，应检查该工作目录的 `.specify/feature.json` 是否指向正确功能。开始新的功能前清除旧的覆盖值：

```powershell
Remove-Item Env:SPECIFY_FEATURE_DIRECTORY -ErrorAction SilentlyContinue
```

PR 评审也检查活动功能指向和机器专属路径，避免合入其他成员的个人工作状态。不要多人共享同一个可写工作目录。

## 8. Git 分支和合并管理

### 基本约定

- `main`：始终能构建，保留可运行的最新集成版本。
- `feat/功能编号-名称`：一项功能或一个可独立检查的阶段。
- `fix/问题名称`：问题修复。
- `chore/变更名称`：工具、构建、依赖或工程维护。

3～4 人先采用这一套，不额外引入长期 `develop`。成员各自克隆仓库。每个分支只有一位主负责人；一位成员可以连续完成多个短分支。

### 日常示例

以下假设 `origin` 已配置、公共基础已合入 `main`、工作区干净：

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/003-inspection-flow
```

开发者完成对应 spec、plan、tasks 和代码后，提交自己的变更。提交前检查文件列表，避免把其他功能或运行数据一起带入。

```powershell
git status --short
git diff
git add -- specs/003-inspection-flow src/Workflow src/Algorithms
git diff --cached
git commit -m 'feat: implement ordinary-part inspection flow'
git fetch origin
git merge origin/main
```

上面的路径仅为示例；新增测试、接口或其他属于该 PR 的文件也应明确加入提交。若合并出现冲突，先完成下面的冲突处理，再继续。无论有无文本冲突，都应重新构建并运行本次改动相关的检查，然后推送：

```powershell
git push -u origin feat/003-inspection-flow
```

在团队 Git 平台创建 PR，目标为 `main`。指定评审人，通过检查后由 A 或指定备份维护人合并；建议统一采用 Squash merge，把该 PR 作为一个清晰变更保留。功能合入后关闭分支，下一个任务从最新 `main` 开新分支。

### 合入条件

1. PR 说明对应功能目录、原需求 ID、任务范围及尚未覆盖的部分。
2. spec、plan、tasks 和实际代码一致；没有恢复已排除功能或私自确定待补充值。
3. 能构建；与此次改动有关的自动检查和模拟流程通过。
4. 接口或数据库变化经维护人评审；依赖它的改动已经合入或纳入同一完整 PR。
5. 至少一位非作者评审通过；设备和流程交界的改动由 B/C 共同核对。
6. 按最新 main 重新检查后合并；看板状态在合入后才标记“已集成”。

仓库平台为 main 配置禁止直接推送、要求评审及构建检查。评审通过是合并动作的前置条件，由团队一次建立规则后持续执行。

### 合并顺序

公共接口／基础工程 → 可独立工作的模拟器与适配器 → 流程与界面模块 → 应用装配及跨模块联调。

依赖已经确定时，先合接口再合调用方。可使用模拟适配器让流程或界面提早合入；不要让主分支依赖尚未存在的另一个人的分支。每次合并之后，剩余成员获取最新 main。

### 冲突处理

- 普通代码：分支作者先处理，涉及其他模块时请维护人核对。
- 公共接口、状态枚举、公共构建配置：A 组织相关调用方一起确认。
- 数据库 schema 与迁移：D 维护，3 人时 A；迁移编号和顺序统一分配。
- `spec.md`／`plan.md`：先明确最终需求与设计，再修改代码；不能只选某一侧文本。
- `tasks.md`：核对实际代码，不能用冲突处理把未实现任务标成完成。
- 不用整批“保留我的版本”解决业务冲突；没有文本冲突也要检查状态、单位和调用时序是否一致。

### 同机多个工作目录的可选方案

每人在不同电脑上开发时，直接各自 clone 即可。如果同一人要在同一电脑同时处理不同功能，可使用 Git worktree 创建独立目录：

```powershell
git fetch origin
git worktree add -b feat/003-inspection-flow '..\gaode-1-flow' origin/main
```

在新目录中单独设置 feature 目录、打开开发会话。该示例与前面的同名分支创建命令二选一；若分支已经存在，不再使用 `-b` 重复创建。worktree 的工作目录隔离机制见[Git 官方文档](https://git-scm.com/docs/git-worktree)。

## 9. 如何跟踪进度和需求变更

建议使用一张团队看板，状态为：待澄清／待开发／开发中／待评审／已集成。每项记录：

| 字段 | 示例 |
| --- | --- |
| 功能／任务标识 | `003-inspection-flow/T012`，避免不同功能里的 T012 混淆 |
| 需求来源 | 对应 TASK、ACQ、ALG 的具体需求 ID |
| 负责人 | C |
| 前置依赖 | 001 公共接口已合入 |
| 分支／PR | `feat/003-inspection-flow` 和对应 PR |
| 完成检查 | 算法超时后保存 Pending，后续工件继续，迟到结果不重触发动作 |
| 待补充 | 关联 OPEN 编号，并说明只影响哪些任务 |

功能执行进度以各自 `tasks.md` 和 PR 为依据；跨功能集成进度以看板为依据。A 定期汇总到需求开发跟踪表，避免 3～4 人同时编辑 Excel 或 Word。

每天短会只核对：今天准备合入什么、需要谁提供哪个接口、是否有跨模块变更。每人同时推进一个主要功能，尽早提交可检查的小 PR。

需求补充先更新相关 spec／决策记录，评估对接口和调用方的影响，再调整 plan、tasks 和代码；跨功能范围变化由 A 维护 SRS 后续版本。已合并 spec 如需演进，用新的分支／PR 更新，保留 Git 历史，不覆盖过去任务的实际完成记录。

## 10. 优先进行的内部检查

围绕具体风险做检查，不为满足数量而堆测试：

- 算法抛错、超时、未配置时可退出等待，保存 Pending 并继续后续可执行步骤。
- 算法迟到结果、重复回调不串件、不重复发出物理动作。
- 当前面整盘批采顺序符合已确认规则，图像关联到正确的工件／面／相机。
- 任务运行时使用配方与点位快照，后台编辑不改变在途任务。
- PLC 断联或动作未完成时，不误记动作完成；恢复不盲目重复执行。
- MES、模型、样本保持未接入时，模拟端到端流程仍可运行。
- Z 或固定点位无效时不下发猜测坐标；模拟配置不会误接真实设备。

这些是开发与合并检查，不构成已移除的交付、培训或验收安排。

## 11. 启动顺序清单

1. 确定 A/B/C/D 对应人员；3 人时 A 兼 D。
2. 统一技术栈、工具版本和目录边界，初始化仓库与 Spec Kit。
3. 审阅项目规范，建立 001 基础功能与公共接口。
4. 合入 001 后，同时启动设备采集、普通件流程、最小界面与记录。
5. 首先演示模拟设备下的成功与算法异常两条流程。
6. 按功能包逐步补齐本期需求，设备协议／现场值补充后接入真实设备。
7. 每个功能通过 PR 合并，持续维护待补充清单与需求覆盖状态。
